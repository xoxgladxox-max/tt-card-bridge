# tt-card-bridge 功能节点树

本文件记录插件有哪些功能、代码在哪、当前状态，以及作者的决定和来源。改功能时同步更新本文件。

状态取值：

- 早期已有：本轮对话之前就有的功能，本轮没有改动，作者没有在本轮手测
- 已部署待手测：代码已改、单元测试通过、已部署，作者还没测
- 有缺陷：已发现问题，还没修
- 计划中：作者已同意，还没写代码
- 作者测过：作者手测通过（目前没有）

文件简称：`svc` = `src/sync-service.mjs`，`eng` = `src/sync-engine.mjs`，`ad` = `src/file-sync-adapter.mjs`，`ids` = `src/world-entry-ids.mjs`，`ui` = `extension/settings.js`，`idx` = `extension/index.js`

## 0 面板布局

从上到下：状态行（连接、同步状态、启动/暂停、刷新、导入酒馆）→ 当前卡（一行状态，只显示用得上的按钮：没拆过显示「拆解当前卡」和拆前清单；有工程原来的卡已不在显示「改连到当前卡」；连着时不显示按钮）→ 消息区（错误、改动清单、结果、备份、恢复预览都在这一处）→ 三个默认收起的折叠区：工作区（工程下拉、备份、拆解世界书）、设置（工作区目录、备份开关和份数、备份位置）、工具（技能检查与同步、日志、复制诊断）。展开状态记在浏览器 localStorage。代码：`ui` mountSettings、renderControls；`extension/style.css`。状态：已部署待手测。

## 5 自动同步

只管酒馆当前打开的那张卡和那本世界书，每 2 秒一轮。

**持续连着和断开后重连分开处理（2026-10-27 作者决定）。** 每轮把工程、酒馆和上次同步存下的记录（`.card-forge/tavern-sync.json`）三方对比。

- 持续连着：这张卡上一轮两边一致，之后作者在任一边改，只改了一边的每 2 秒自动同步过去；两边都改了同一项时停下列清单，必须选。
- 断开后重连：后台重启、暂停后恢复、切走又切回、上一轮出错都算断开。重连后第一轮有差异就把这段时间积累的改动列清单（状态「有改动待确认」），作者确认前两边都不写；没有差异直接进入持续连着。
- 清单逐项给出建议：只改了工程的建议用工程，只改了酒馆的建议用酒馆，两边都改的不给建议。每项显示工程文件和酒馆文件的修改时间，只作参考，不按时间自动选边；酒馆的时间是整张卡或整本世界书文件的时间。
- 作者可以逐项选（工程 / 酒馆 / 手写），也可以选「整卡以文件为准」或「整卡以酒馆为准」；都先列清单确认，按备份设置备份后再执行，执行后复核，一致后进入持续连着。
- 手动的推送、拉回、MCP `sync_now` 由调用者明确发起，不在此列。

## 9 出错时怎么处理（计划中）

作者已确认方案（2026-10-27），还没写代码。

### 9.1 什么时候检查

| 时机 | 查什么 | 写不写 |
|---|---|---|
| 切卡 | 当前打开的这张卡 | 只读 |
| 点「刷新」 | 工作区里全部工程，加当前卡 | 只读 |
| 点「启动同步」 | 同刷新 | 只读 |
| 之后每 2 秒 | 不做检查，只做第 5 节的普通同步 | 按第 5 节 |

检查结果显示为清单。全部正常就开始同步；有问题只暂停这张卡，其他卡不受影响，并在每项问题旁给出处理按钮。出错后不自动重试，等作者处理后点「刷新」。

### 9.2 检查项

1. 连接与工作区：后台能否连上，工作区目录是否存在
2. 当前卡有没有工程，是否被多个工程重复绑定
3. 删卡重导留下的工程：原来连的卡已不在酒馆里，提示改连
4. 世界书：卡绑定的世界书文件是否存在，和工程里记的是否一致
5. 本地格式：文件开头设置能否解析、`<!-- body -->` 是否缺失或重复、是否是旧版节点结构
6. 条目编号：缺 `id`、编号重复、编号被酒馆其他条目占用
7. 上次写入或恢复没有完成
8. `待归位\` 里还有没处理的内容
9. 差异：哪些可以按第 5 节自动同步，哪些需要作者选边

### 9.3 错误分五类

后台为每个错误附上类别、涉及的文件和修复办法。

| 类别 | 例子 | 处理按钮 |
|---|---|---|
| 后台连不上 | 连接失败、启动超时、缺连接配置 | 启动同步、重新安装 |
| 工程和卡对不上 | 卡已不在、重复绑定、卡被其他工程接管、世界书绑定不同 | 改连、解除绑定、合成导入、拆解覆盖（都先预览） |
| 本地文件问题 | 缺正文标记、开头设置写坏、缺 id、编号重复或被占 | 一键修复：补正文标记、补 id、重新编号 |
| 两边不一致 | 两边都改了同一项、重连后有积累改动、设置或结构差异 | 逐项选边、整卡选边（第 5 节） |
| 上次操作没完成 | 写入结果待确认、需要人工复核、恢复未完成 | 查看、放弃记录、从备份恢复（现有出口待核对） |

### 9.4 修复顺序

每次修复都按同一顺序：暂停这张卡 → 列出将要改动的清单，作者确认 → 按备份设置备份 → 执行 → 复核，两边一致才恢复同步 → 记日志。

### 9.5 条目对齐

改连、编号被占用、拆解覆盖共用同一套规则：按标题和正文配对；配上的条目补固定 `id`，并统一改成酒馆的编号；标题相同、正文不同的交作者选。改连在工程出错时也能点；先算配对，最后才写绑定。
